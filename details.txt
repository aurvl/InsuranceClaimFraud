DETAILS DU PROJET
Insurance Claim Counterfactual Simulator

Ce fichier explique le pipeline actuel, les artefacts encore actifs, la logique
de selection du modele et la signification des donnees.

IMPORTANT

- toutes les donnees sont synthetiques
- la source analytique officielle est PostgreSQL
- le pipeline actif ne repose plus sur des CSV intermediaires
- le modele de prod n'utilise plus un threshold fixe a 0.5

===============================================================================
1. OBJECTIF PRINCIPAL
===============================================================================

Le coeur du projet est la decision interpretable autour de la fraude.

Question centrale:

"Que faudrait-il changer dans un sinistre pour qu'il ne soit plus considere
comme frauduleux ?"

Le modele de fraude est donc un moteur de decision support, pas seulement un
classifieur.

Ce que le projet veut montrer:

- extraction documentaire locale
- structuration des donnees dans PostgreSQL
- travail SQL realiste pour analystes et data scientists
- benchmark de modeles
- optimisation du threshold de decision
- production scoring via FastAPI
- contre-factuels pour expliquer les decisions

===============================================================================
2. PIPELINE ACTUEL
===============================================================================

Le pipeline actif est:

1. un package client arrive sous forme de JSON + PDF + image
2. le module d'extraction lit et consolide ces sources
3. le dossier structure est insere dans PostgreSQL
4. les analyses SQL et l'entrainement lisent PostgreSQL
5. la partie ML benchmarke plusieurs approches
6. le systeme choisit un champion de deploiement
7. FastAPI score les nouveaux dossiers avec ce champion
8. le systeme peut produire un contre-factuel

Le pipeline ne fait plus:

- de CSV comme etape intermediaire entre extraction et base
- de selection du modele uniquement sur l'AUC
- de decision finale basee sur un threshold fixe a 0.5

===============================================================================
7. NOUVELLE LOGIQUE TRAINING
===============================================================================

Le pipeline actuel de training ne se contente plus d'entrainer un modele puis
d'appliquer 0.5.

Il fait maintenant:

1. split historique en train / validation / holdout
2. benchmark de plusieurs modeles
3. benchmark de plusieurs strategies d'equilibrage par modele
4. tuning du threshold sur validation
5. selection d'un champion de deploiement

Objectif de selection:

- maximiser la precision
- imposer un rappel minimal de 0.20
- utiliser F1 et ROC AUC comme signaux secondaires

Cela correspond mieux a un contexte fraude ou une precision trop basse rend le
modele difficile a presenter ou a utiliser operationnellement.

===============================================================================
8. MODELES ET STRATEGIES ACTUELLES
===============================================================================

Candidats du benchmark actif:

- rf avec weighted imbalance handling
- xgb avec oversample imbalance handling

Le SVM existe encore dans le code, mais il n'est plus retenu dans le benchmark
de deploiement car il est trop couteux sur ce volume pour un gain peu utile.

Champion actuel:

- classifier: xgb
- selected_imbalance_strategy: oversample
- decision_threshold: 0.83

Alternative benchmarkee:

- rf
- selected_imbalance_strategy: weighted
- decision_threshold: 0.76

===============================================================================
12. ROLE DE FASTAPI
===============================================================================

FastAPI sert a la partie operationnelle:

- intake package
- extraction
- validation
- scoring
- insertion SQL
- contre-factuels

Point important:

- FastAPI lit le champion de deploiement
- la decision applique le threshold appris et retenu pendant le benchmark

Donc, si le champion actuel est xgb avec threshold 0.83, l'API suit cette
decision, pas un threshold arbitraire de 0.5.
